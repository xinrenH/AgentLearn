# 阶段3：RAG 知识库问答 — 学习任务说明文档

> **定位**：让 Agent 能基于你的私有文档回答问题。这是企业中最常见的 Agent 应用模式，面试必考。
> **前置条件**：完成阶段 2（Agent Tool Calling），能创建 Agent 并注册工具。
> **总时长**：每天 2 小时，约 2-3 周完成。

---

## 学习前必读：RAG 到底在解决什么问题？

**LLM 的两大缺陷**：
1. 知识截止到训练日期，不知道最近发生的事
2. 不知道你的私有文档（公司制度、产品手册、个人笔记）

**RAG 的解决方案**：
```
用户提问： "公司年假政策是什么？"
  ↓
1. 检索（Retrieve）：从你的文档库里找出最相关的几段
  ↓
2. 增强（Augment）：把检索到的文档片段拼到 prompt 里
  ↓
3. 生成（Generate）：LLM 基于你给的文档片段 + 原始问题 → 生成回答
```

**关键认知**：RAG 的核心瓶颈不是 LLM，而是"检索质量"。文档切得不好、检索不准，再好的 LLM 也白搭。

## 学习任务 1：理解 Embedding 与向量检索

### 任务目标
理解 Embedding 是什么，能用向量数据库做相似度检索。

### 学习内容
- Embedding：把文字转成一串数字（向量），语义相近的文字向量距离近
- 余弦相似度：衡量两个向量的相似程度
- 向量数据库：专门存储和检索向量的数据库（ChromaDB 最简单）
- 为什么用向量数据库而不是传统数据库：传统 DB 搜"苹果手机"找不到"iPhone"

### 实战练习

| # | 练习 | 具体要求 |
|---|------|---------|
| 1.1 | 安装 ChromaDB | `pip install chromadb`，零配置启动 |
| 1.2 | 生成 Embedding | 用 `openai.embeddings.create(model="text-embedding-3-small")` 给几段文本生成向量，观察向量维度（1536 维） |
| 1.3 | 计算相似度 | 手写余弦相似度函数，计算"苹果手机"和"iPhone 15"的 embedding 相似度，vs "苹果手机"和"香蕉"的相似度 |
| 1.4 | ChromaDB 存和查 | 把 10 段文档存入 ChromaDB，查询时按相似度返回 top-3 |
| 1.5 | 阈值过滤 | 只返回相似度 > 0.7 的结果，低于阈值的返回空（避免 LLM 编造） |

### 产出物
- `embedding_demo.py` — Embedding 生成、相似度计算、ChromaDB 操作
- 一份对比表：不同阈值对检索结果的影响

### 验收标准
- 理解 Embedding 是一串数字，相似内容的向量距离更近
- 能用 ChromaDB 存文档、按相似度检索
- 理解为什么需要相似度阈值

## 学习任务 2：文档加载与切分

### 任务目标
能加载多种格式的文档（PDF、TXT、Markdown），并合理切分成小块。

### 学习内容
- 文档加载器：`PyPDFLoader`、`TextLoader`、`UnstructuredMarkdownLoader`
- **切块策略**是 RAG 最重要的调参项：
  - `chunk_size`：每块多大（太大检索不准，太小语义不完整）
  - `chunk_overlap`：块与块之间重叠多少（防止关键信息被切断）
- `RecursiveCharacterTextSplitter` 的递归切分逻辑
- 不同文档类型的不同处理方式

### 实战练习

| # | 练习 | 具体要求 |
|---|------|---------|
| 2.1 | 加载 PDF | 找一篇 PDF 论文或文档，用 `PyPDFLoader` 加载，提取全文 |
| 2.2 | 基础切分 | 用 `RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=200)` 切分 |
| 2.3 | 切块大小实验 | 同一文档用 chunk_size=256 / 512 / 1024 / 2048 分别切分。存入 4 个 ChromaDB 集合。用 5 个同样的问题检索，人工评分。找出最佳 chunk_size |
| 2.4 | 语义切分 | 用 `SemanticChunker`（基于 embedding 相似度的智能切分），对比固定长度切分的检索效果 |
| 2.5 | 文档元数据 | 切块时保留元数据（来源文件名、页码、章节标题）。检索时能显示每条结果来自哪个文档的哪一页 |

### 产出物
- `document_loader.py` — 文档加载 + 多种切分方式
- 一份实验报告：不同 chunk_size 的检索准确率对比（至少 5 个问题的数据）
- 一个包含元数据的检索结果展示

### 验收标准
- 能加载 PDF/TXT/MD 并切分成合理的文本块
- 知道 chunk_size 对检索效果的影响，能根据文档类型选择合适的值
- 检索结果能追溯到来源文档和位置

## 学习任务 3：搭建完整 RAG 链路

### 任务目标
从零搭建一条完整的 RAG 链路：文档入 → 切分 → Embedding → 存向量库 → 用户问 → 检索 → LLM 回答。

### 学习内容
- RAG 的完整数据流
- Prompt 模板设计（把检索到的文档拼进去）
- LangChain 的 `RetrievalQA` 链（或自己手写拼接逻辑）
- 引用溯源：回答里标注信息来源

### 实战练习

| # | 练习 | 具体要求 |
|---|------|---------|
| 3.1 | 端到端 RAG | 找 3-5 篇你自己写的或感兴趣的文档，走通完整 RAG 链路 |
| 3.2 | RAG Prompt 模板 | 设计 prompt：`"请基于以下资料回答问题。如果资料中没有相关信息，请明确说'未找到相关信息'，不要编造。\n\n资料：\n{context}\n\n问题：{question}"` |
| 3.3 | 引用标注 | 回答时要求 LLM 在每句话后标注来源编号，如 `[来源1]`。前端展示时能点击跳转到原文 |
| 3.4 | 空结果处理 | 当检索结果全部低于相似度阈值时，返回"抱歉，知识库中没有相关信息"而不是让 LLM 自由发挥（编造） |

### 产出物
- `rag_pipeline.py` — 完整的 RAG 链路（加载→切分→向量化→检索→回答）
- 一个可用的知识库（你自己的文档集合）
- 至少 10 个测试问答，记录回答准确率和来源命中率

### 验收标准
- 走通完整 RAG 链路，能基于文档回答问题
- 回答能追溯到具体文档片段
- 知识库中没有的信息不会编造

## 学习任务 4：检索质量优化

### 任务目标
提升检索的"命中率"——搜出来的东西和问题相关。

### 学习内容
- 检索的常见问题：搜不准（不相关）、搜不全（遗漏相关）、搜到噪音（干扰 LLM）
- **重排序（Reranking）**：先用向量检索召回 top-20，再用更精确的模型重排取 top-3
- **查询重写（Query Rewriting）**：用户问"昨天那个事怎么样了"→ LLM 先改成"XX 项目的 XX 问题当前进展"
- **混合检索（Hybrid Search）**：向量检索 + 关键词检索（BM25）结合，互补短板
- **HyDE（假设文档嵌入）**：先让 LLM 假设一个答案，用假设答案的向量去检索

### 实战练习

| # | 练习 | 具体要求 |
|---|------|---------|
| 4.1 | 重排序实验 | 检索 top-20 → 用 `CohereRerank` 或 `sentence-transformers` 的 CrossEncoder 重排 → 取 top-3。对比重排前后的检索准确率 |
| 4.2 | 查询重写 | 用 LLM 把用户模糊的原始问题改写成更精准的检索查询。对比改写前后的检索效果 |
| 4.3 | 混合检索 | 向量检索 + BM25 关键词检索，结果取并集后重排。对比单一向量检索的召回率 |
| 4.4 | 多轮 RAG | 用户连续追问时（"刚才那个文档里还说了什么？"），用对话历史优化检索查询。实现：用历史 + 当前问题 → LLM 生成独立的检索查询 |

### 产出物
- `retrieval_optimizer.py` — 含重排序、查询重写、混合检索的优化模块
- 一份对比报告：优化前 vs 优化后的检索命中率（Precision@3 / Recall@10）

### 验收标准
- 能对检索结果做重排序，提升 top-3 的相关性
- 能对模糊查询做重写，提升检索精准度
- 有量化的优化数据（如命中率从 60% 提升到 85%）

## 学习任务 5：进阶 RAG 模式

### 任务目标
掌握更高级的 RAG 模式，不再只是"搜一段 → 回答"。

### 学习内容
- **Self-RAG**：Agent 判断需要检索时才检索，不需要时不调（节省成本）
- **Corrective RAG**：检索后评估文档质量，不合格则重搜
- **Multi-Hop RAG**：回答一个复杂问题需要多次检索（第一次搜 A，基于 A 的结果再搜 B）
- **Agentic RAG**：用 Agent 的 Tool Calling 能力做 RAG——检索只是一个工具

### 实战练习

| # | 练习 | 具体要求 |
|---|------|---------|
| 5.1 | 条件检索 | 写一个判断器：用户问题是否需要检索？("今天天气怎么样"需要 / "讲个笑话"不需要) |
| 5.2 | 质量评估 | 检索后自动评估每段文档和问题的相关性（用 LLM 打分 1-5），低于 3 分的丢弃 |
| 5.3 | Multi-Hop | 实现"对比型"问答：用户问"A 产品和 B 产品有什么区别"，先检索 A 的信息，再检索 B，最后 LLM 对比 |
| 5.4 | Agentic RAG | 把检索功能封装成 Agent 的一个 tool（`search_knowledge_base(query: str)`），Agent 自己决定什么时候搜、搜几次 |

### 产出物
- `advanced_rag.py` — 多种进阶 RAG 模式的实现
- 每个模式的测试用例和效果对比

### 验收标准
- 能实现至少 2 种进阶 RAG 模式
- 理解什么时候该用哪种模式

## 学习任务 6：综合实战 — 本地知识库问答系统

### 任务目标
做一个完整、可用、能演示的本地知识库问答系统。

### 功能需求

```
本地知识库问答系统
==================
功能：
1. 文档管理
   - 上传 PDF / TXT / Markdown 文档
   - 自动切分、生成 embedding、存入向量库
   - 查看已索引的文档列表

2. 问答
   - 自然语言提问，返回基于文档的回答
   - 每条回答标注引用来源（文件名 + 页码/段落号）
   - 知识库中没有的信息明确告知用户

3. 检索优化
   - 默认使用重排序（粗排 top-20 → 精排 top-3）
   - 查询自动重写（模糊问题 → 精准检索查询）

4. 评测
   - 内置 20 条测试问答（含预期答案）
   - 自动计算：答案准确率、检索命中率、平均延迟
   - 输出评测报告

5. 交互
   - CLI 界面（优先级高）或简单的 Web 界面（FastAPI + 静态页）
   - 显示每次检索的相似度分数
```

### 技术要求
- 向量数据库：ChromaDB（本地运行，零配置）
- Embedding 模型：OpenAI `text-embedding-3-small`
- LLM：gpt-4o-mini（推理）+ gpt-4o（评测/困难问题）
- 重排序：`sentence-transformers` 的 `cross-encoder/ms-marco-MiniLM-L-6-v2`
- 文档加载：`PyPDF2` + `python-docx` + `markdown`
- 完整日志：每次问答记录检索耗时、结果数、LLM 耗时

### 产出物
- `kb_system/` 项目目录，含：
  - `main.py` — 入口
  - `loader.py` — 文档加载与切分
  - `indexer.py` — Embedding + 向量库存入
  - `retriever.py` — 检索 + 重排序
  - `qa.py` — 问答逻辑
  - `evaluate.py` — 评测模块
  - `test_questions.json` — 20 条测试问答
- `README.md` — 使用说明 + 评测报告

### 验收标准
- 上传 ≥ 3 篇文档后，能基于内容问答
- 回答能追溯到具体文档位置
- 评测集 20 题准确率 > 70%（评估模式）
- 单次问答延迟 < 3 秒（不含 LLM 生成时间）
- 知识库外的问题能明确说"不知道"而非编造
