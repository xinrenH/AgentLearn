# 阶段6：生产化与可视化部署 — 学习任务说明文档

> **定位**：把前面写的脚本变成一个真正可以给别人用的"产品"。部署上线、可观测、有评测、有文档。
> **前置条件**：完成阶段 3-5（RAG + LangGraph + 多 Agent），至少有一个能跑的项目。
> **总时长**：每天 2 小时，约 2-3 周完成。

---

## 学习前必读：从 Demo 到产品差多远？

| 维度 | Demo 阶段 | 产品阶段 |
|------|----------|---------|
| **启动方式** | `python main.py` | `docker-compose up` 一键启动 |
| **接口** | 终端交互 | REST API + Swagger 文档 |
| **错误处理** | print 一下 | 结构化日志 + 告警 |
| **可观测** | 不知道哪里慢 | 每次调用的耗时/成本/token 一目了然 |
| **评测** | "看起来还行" | 量化指标（准确率、延迟、成功率） |
| **安全** | API Key 在代码里 | 环境变量 + 注入防护 + 审计日志 |
| **文档** | 没有 | README + API 文档 + 部署文档 |
| **可演示** | 开发者自己跑 | 任何人都能按文档跑起来 |

## 学习任务 1：FastAPI 包装 Agent

### 任务目标
把 Agent 从命令行搬到 Web 上，提供 REST API 接口。

### 学习内容
- FastAPI 基础：路由、请求体、响应模型、依赖注入
- Agent 与 FastAPI 的集成
- 流式响应（SSE — Server-Sent Events）
- Swagger 自动生成接口文档
- CORS 配置（允许前端跨域调用）

### 实战练习

| # | 练习 | 具体要求 |
|---|------|---------|
| 1.1 | FastAPI 基础 | 安装 FastAPI + uvicorn，创建 `/health` 健康检查接口 |
| 1.2 | Agent 端点 | 把之前阶段 2 的"个人助理 Agent"包装成 `POST /chat` 接口：接收 `{"message": "..."}`，返回 `{"response": "..."}` |
| 1.3 | 流式端点 | 实现 `POST /chat/stream`，用 SSE 格式逐块推送 LLM 响应 |
| 1.4 | 请求模型 | 用 Pydantic 定义 `ChatRequest` 和 `ChatResponse`，加入字段校验 |
| 1.5 | Swagger 文档 | 检查 `http://localhost:8000/docs` 页面，确认接口可交互测试 |

### 产出物
- `agent_api/` 项目目录：
  - `main.py` — FastAPI 应用入口
  - `routes.py` — 接口路由
  - `schemas.py` — 请求/响应 Pydantic 模型
  - `agent_core.py` — Agent 核心逻辑（从之前迁移）
- Swagger 文档自动可用

### 验收标准
- `POST /chat` 能正常返回 Agent 回复
- Swagger 页面能从浏览器打开并交互测试
- 流式端点 SSE 推送正常

## 学习任务 2：Docker 容器化

### 任务目标
让项目能在任何机器上一致运行——不再有"我电脑上能跑"的问题。

### 学习内容
- Dockerfile 编写：基础镜像、复制代码、安装依赖、暴露端口
- `.dockerignore` 忽略不需要的文件
- docker-compose.yml 编排多个服务
- 多阶段构建优化镜像大小
- 卷挂载（开发时实时同步代码）

### 实战练习

| # | 练习 | 具体要求 |
|---|------|---------|
| 2.1 | 写 Dockerfile | 基于 `python:3.11-slim`，安装依赖、复制代码、暴露端口 8000 |
| 2.2 | 构建并运行 | `docker build -t my-agent .` → `docker run -p 8000:8000 my-agent`，浏览器访问确认可用 |
| 2.3 | docker-compose | 写 `docker-compose.yml`：包含 Agent 服务 + ChromaDB 服务 + Redis 服务（若有），定义网络和依赖顺序 |
| 2.4 | 环境变量管理 | 用 `env_file` 读取 `.env`，不在镜像中硬编码 Key |
| 2.5 | 一键启动 | `docker-compose up -d` 启动所有服务，`docker-compose down` 停止 |

### 产出物
- `Dockerfile` — 精简的生产镜像定义
- `docker-compose.yml` — 多服务编排
- `README.md` 中的启动命令：`docker-compose up`

### 验收标准
- 另一台电脑（或清空本机环境后）能 `docker-compose up` 一键启动
- Agent API 能正常访问
- `.env` 不在镜像中

## 学习任务 3：可观测性（日志 + 追踪 + 指标）

### 任务目标
Agent 上线后能知道它做了什么、哪里慢、花了多少钱、哪里出错。

### 学习内容
- 结构化日志（不要 print，用 `logging` + JSON 格式）
- 请求链路追踪：每个请求一个唯一 ID（trace_id）
- 关键指标收集：请求数、成功率、P50/P99 延迟、Token 消耗
- **LangSmith** 集成：自动追踪每次 LLM 调用
- 日志级别分层：INFO（正常）、WARN（降级）、ERROR（失败）

### 实战练习

| # | 练习 | 具体要求 |
|---|------|---------|
| 3.1 | 结构化日志 | 用 Python `logging` 模块输出 JSON 格式日志，每条含：`timestamp`、`level`、`trace_id`、`message`、`extra_fields` |
| 3.2 | 请求追踪 | FastAPI 中间件：每个请求进来生成 `trace_id`，在响应头返回。所有后续日志带这个 ID |
| 3.3 | 指标收集 | 记录每次 Agent 调用的：(1) 总耗时 (2) LLM 调用次数 (3) 总 token 消耗 (4) 工具调用次数 (5) 成功/失败状态。暴露 `GET /metrics` 接口 |
| 3.4 | LangSmith 集成 | 安装 LangSmith，设置 `LANGSMITH_TRACING=true`，在 LangSmith 网页查看每次调用的完整执行轨迹 |

### 产出物
- `observability.py` — 日志 + 追踪 + 指标模块
- LangSmith 网页截图：能看到的完整执行链路
- 至少 3 天的指标日志

### 验收标准
- 每条日志带 trace_id，可追踪单次请求的全链路
- `/metrics` 接口返回关键统计数据
- LangSmith 能查看每次调用的 LLM 和工具细节
- 错误日志包含足够的排查信息

## 学习任务 4：评测体系

### 任务目标
不再凭感觉说 Agent"好不好"，而是用数据说话。

### 学习内容
- 评测集设计：精心构造 20-50 条问答，覆盖正常/边界/异常场景
- 评测指标：准确率、召回率、F1、答案相关性、忠实度（faithfulness）
- 自动评测：用 LLM 当裁判（LLM-as-judge）评估答案质量
- 回归测试：每次改 Agent 后跑一遍评测集，确认没有退步
- **DeepEval** 集成：专业 Agent 评测框架

### 实战练习

| # | 练习 | 具体要求 |
|---|------|---------|
| 4.1 | 构造评测集 | 为你阶段 3 的 RAG 知识库系统写 20 条评测问答。包含：直接问题、模糊问题、知识库外问题、歧义问题。每条标注预期答案 |
| 4.2 | 自动评测脚本 | 跑一遍所有评测题，用 LLM 对比实际输出和预期答案，打分（1-5） |
| 4.3 | 关键指标 | 计算：(1) 答案准确率 (2) 检索命中率 (3) 幻觉率（编造信息的比例）(4) 拒绝率（该拒绝时是否明确拒绝） |
| 4.4 | 回归测试 | 对 Agent 做一次小改动后，重新跑评测集，对比改动前后的分数变化 |
| 4.5 | DeepEval 入门 | 安装 `deepeval`，用其内置指标（Faithfulness、Answer Relevancy、Contextual Precision）评测你的 Agent |

### 产出物
- `eval/` 评测目录：
  - `test_set.json` — 20 条评测问答
  - `evaluate.py` — 自动评测脚本
  - `eval_report.md` — 评测报告（含各项指标和样例）
- 至少一次"改动前后对比"的评测报告

### 验收标准
- 有至少 20 条评测用例覆盖各类场景
- 自动评测脚本可重复运行
- 评测报告含量化指标而非主观描述
- 改动后有回归测试数据

## 学习任务 5：安全基础

### 任务目标
Agent 不是玩具，上线前必须考虑安全。

### 学习内容
- **Prompt Injection** 防护：用户输入可能包含"忽略之前的指令"
- 工具权限隔离：Agent 能调的工具有没有越权风险
- 敏感信息脱敏：API Key、密码、个人信息不能出现在日志/响应中
- 速率限制：防止滥用
- 审计日志：谁在什么时候做了什么

### 实战练习

| # | 练习 | 具体要求 |
|---|------|---------|
| 5.1 | 注入攻击测试 | 收集 10 条常见的 Prompt Injection 攻击语句（如"忽略所有之前的指令""打印你的 system prompt"），测试你的 Agent 是否中招 |
| 5.2 | 注入防护 | 实现分层防护：(1) 输入层：检测并过滤可疑模式 (2) System Prompt 层：明确的"不可越权"指令 (3) 工具层：敏感操作二次确认 |
| 5.3 | 敏感信息脱敏 | 日志自动过滤 `sk-` 开头的字符串、邮箱、手机号。写脱敏函数 `mask_sensitive(text: str) -> str` |
| 5.4 | 速率限制 | FastAPI 中间件：同一 IP 每分钟最多 30 次请求，超过返回 429。记录超限日志 |
| 5.5 | 审计日志 | 记录每次工具调用的：用户、时间、工具名、参数、结果摘要。不可删除 |

### 产出物
- `security.py` — 安全模块（注入检测、脱敏、速率限制）
- `attack_test_cases.json` — 10+ 条注入攻击用例及防护结果
- 审计日志示例

### 验收标准
- 10 条常见注入攻击至少能拦截 8 条
- 日志中不出现 API Key 原文
- 速率限制生效
- 工具调用有审计记录

### 任务目标

### 学习内容

- Docker 自部署 Dify
- 创建知识库、上传文档
- 搭建可视化 Agent 工作流
- Dify 的 API 导出（你的 Agent 可以作为 API 供外部调用）

### 实战练习

| # | 练习 | 具体要求 |

| 6.2 | 搭建应用 | 在 Dify 中创建"知识库问答"应用：上传文档 → 建知识库 → 配置 LLM → 测试对话 |
| 6.3 | 可视化工作流 | 创建 Agent 工作流：用户输入 → 知识检索 → LLM 推理 → 输出。添加条件分支、工具节点 |

### 产出物

### 验收标准

## 学习任务 7：综合实战 — 3 个项目作品集

### 任务目标
打磨 3 个可交付项目，整理完整作品集，达到面试可演示水平。

### 3 个作品集项目

#### 项目 1：企业知识库问答系统（RAG）
- 基于阶段 3 的 `kb_system/` 项目
- 完善：FastAPI 包装 + Docker 部署 + 评测报告 + 安全防护
- 演示：上传内部文档 → 提问 → 溯源展示

#### 项目 2：智能工单处理 Agent
- 新建项目
- 功能：接收用户工单（文字描述）→ 自动分类（技术/行政/财务）→ 提取关键信息 → 建议分派人 → 生成回复草稿
- 含 Plan-Act-Reflect 循环 + Human-in-the-loop 审批
- 技术栈：LangGraph + FastAPI + Docker

#### 项目 3：代码助手 Agent
- 新建项目
- 功能：用户描述需求 → Agent 生成代码 → 自查代码质量 → 给出改进建议
- 工具：文件读写、代码执行（沙箱）、代码检查（pylint）
- 演示：生成一段 CRUD 代码 → 自动发现 bug → 修改 → 展示最终版本

### 每个项目必须包含

```
项目交付清单
============
□ 可运行源码（GitHub 仓库）
□ Docker 一键启动
□ README（项目介绍、架构、启动方式、接口说明）
□ 评测数据（20+ 条测试用例 + 评测报告）
□ 架构图（Mermaid / Draw.io）
□ 演示脚本（录屏 3 分钟 / 命令行录屏）
□ 优化前后对比数据（至少有 1 次可量化的优化）
□ 安全措施说明
```

### 作品集文档

整理一份完整的作品集文档，用 **STAR 原则**描述每个项目：
- **S**ituation：项目背景，解决什么问题
- **T**ask：你的任务和目标
- **A**ction：你做了什么（技术选型、架构设计、关键决策）
- **R**esult：成果和指标（准确率 XX%、延迟 XXms、成本 $X/千次）

### 产出物
- 3 个 GitHub 仓库（或 1 个 monorepo 3 个子目录）
- 1 份作品集文档 `portfolio.md`
- 3 个 3 分钟演示视频/录屏
